# 交付文件規範(QA-DS 1.0)

平台內部只有一個測試結論,算法見 [驗收標準與測試報告規範(PA-AS 1.0)](./acceptance-standard.md)。本文件規範的是**另一件事**:把那個結論與它的證據,重新表述成客戶品檢流程要求的交付文件。

兩套語彙並存,互不覆寫:

| | 內部判定(PA-AS) | 交付文件(QA-DS) |
|---|---|---|
| 逐項結果 | pass / fail / unclear / skipped | PASS / FAIL / BLOCK / N-A |
| 整體結論 | PASS / PASS_WITH_RISK / FAIL / BLOCKED | 沿用內部結論,不重算 |
| 缺陷嚴重度 | critical / high / medium / low | A 級致命 / B 級嚴重 / C 級缺陷 / D 級建議 |
| 發現分級 | 無 | E0 / E1 / E2 / E3 |
| 通過率 | 通過 ÷(通過＋失敗) | PASS ÷ 測試用例執行總數 |

**投影不是第二次判定。** 結論、缺陷歸因與驗收項目全部沿用 PA-AS 的結果;QA-DS 只換語彙、換版面、補上客戶文件要求的欄位。兩個通過率的分母不同,報告上一律並列並標明分母,不互相取代。

實作:`infra/lambda/api/report/qaDocs.ts`(純函式,只讀 `StructuredReport` 既有欄位)。前端:`web/src/components/report/QaDocsPanel.tsx` 與匯出整形 `qaDocsExport.ts`。測試:`infra/test/report-qa-docs.test.ts`、`web/src/components/report/qaDocsExport.test.ts`。

## 1. 結果狀態

| 狀態 | 定義 |
|---|---|
| PASS | 實際執行結果與預期符合 |
| FAIL | 實際執行結果與預期不符合 |
| BLOCK | 不具備可執行條件 |
| N/A | 本次版本未包含用例描述功能 |

對應關係:

| 內部值 | 交付值 | 說明 |
|---|---|---|
| `pass` | PASS | |
| `fail` | FAIL | |
| `unclear` | **BLOCK** | 已執行但證據不足以判定;原判定寫在備註 |
| `skipped` | **BLOCK** | 沒有後續畫面可判定該步預期;原判定寫在備註 |
| 驗收項目 `not_evaluable` | BLOCK | |
| 驗收項目 `not_applicable` | N/A | 四態中唯一會落到 N/A 的來源 |

**未執行與無資料不填 PASS。** 這條規則寫在 `qaResultOfCheck()` 的型別裡:四態之中沒有「待判讀」,而把待判讀折到 PASS 會讓一份測試看起來比實際乾淨。折到 BLOCK 會讓結論偏保守,這是刻意的 —— 保守的代價是重測,樂觀的代價是放行一個沒驗過的版本。

允收欄位只有 PASS 記 `Y`;N/A 既不是允收也不是退回,記 `—`。

## 2. 缺陷嚴重度與發現分級

嚴重度由內部 severity 直接對應:`critical→A`、`high→B`、`medium→C`、`low→D`。

發現分級沒有對應來源,由規則推導,**順序固定且附理由**(分級要能被覆核,不能只給一個字母):

1. 歸因為環境(`ENVIRONMENT`)或類別屬 `network` / `compatibility` → **E3 特殊環境造成**
2. D 級建議(`low`)→ **E0 已知問題與優化建議**
3. 重現性 `always` / `frequent` → **E1 一般操作觸發**
4. 其餘 → **E2 滿足特定流程或條件觸發**

優先權(P0~P3)由嚴重度推導,並在欄位標題標明是推導值 —— 原文件這一欄是人工填的,不標會被誤認為客戶既有的分派結果。

**測試工具問題不算遊戲缺陷。** 平台把 AI 代理自身的失敗(點錯、解析失敗)與遊戲缺陷分開,客戶的問題清單沒有對應欄位。這些列進 T05 的獨立表格「測試工具問題(不計入遊戲缺陷)」,不混入缺陷統計。

## 3. 統計指標

三個公式保留原分母,不以新指標名稱替換:

| 指標 | 公式 | 定義界線 |
|---|---|---|
| 測項覆蓋率 | 定版測項 ÷(定版測項＋新增測項) | 定版測項占比,**不是需求覆蓋率** |
| 執行通過率 | PASS ÷ 測試用例執行總數 | 執行總數的納入範圍須隨報告確認 |
| Bug 修正率 | (已修正＋不做處理)÷ Bug 總數 | 分子含不做處理,**不能解讀為全數實際修復** |

每個指標都外顯 `numerator` / `denominator` / `basis` / `caveat`。只給百分比會被誤讀:三個分母分別是測項母體、已執行列數、缺陷總數。

**算不出來就回 null。** 與 `metrics.ts` 的 `not_collected` 同一原則:

- 測項覆蓋率需要測項母體。單次執行報告沒有母體 → `null`,附原因。
- Bug 修正率需要跨版本的處理狀態。本次執行的缺陷全是開立狀態 → `null`,附原因。
- 兩者都可由 `QaDocOptions`(`itemBaseline`、`defectDisposition`)補入後計算。
- 分母為 0 時回 `null`,不回 0%。

執行通過率的分母是「已執行列數」= 通過＋失敗＋待判讀,不含未執行與不適用。這與平台內部通過率(通過÷(通過＋失敗),受阻不進分母)不同,兩者的 `caveat` 都寫明不可互換。

## 5. 19 類交付文件

文件集永遠列出全部 19 類。單次自動化執行無法產生的,標 `not_derivable` 並寫明原因,**不靜默省略** —— 「完整」指的是覆蓋狀態完整,不是硬填。

| 覆蓋狀態 | 意思 |
|---|---|
| `derived` | 單次執行即可填滿工作紀錄 |
| `derived_with_gaps` | 可填主要欄位,需人工補填的欄位逐項列在 `unfilled` |
| `not_derivable` | 本文件的輸入不是執行證據 |

| 文件 | 群組 | 覆蓋 | 資料來源 / 不可產生的原因 |
|---|---|---|---|
| T01 送測前檢驗 | 送測與規劃 | gaps | 可測性與阻擋原因來自終局狀態;送測版本的基本操作條件須人工確認 |
| T02 專案測試項目與允收表 | 送測與規劃 | gaps | 一列一個驗收項目(門檻、實際值、允收 Y/N);主管簽核須人工 |
| T03 詳細測試項目與執行結果 | 執行與結果 | gaps | 一列一個逐步判定,附分類、交叉標籤與缺陷代碼。原表一列記兩個平台:平台A為本次受測平台,平台B全列「未測」(見下) |
| T04 測項會議紀錄 | 送測與規劃 | — | 輸入是測項草稿的討論與決議,屬人工會議紀錄 |
| T05 問題清單 | 問題與複驗 | gaps | 缺陷附 A~D 級、E0~E3 與頻率;分配、修正與複驗版本屬後續版本 |
| T06 專案問題紀錄表 | 問題與複驗 | gaps | 問題描述與填寫日期可產生;解決方式與確認日期須修正後補填 |
| T07 版本測試結案報告 | 結案與交付 | gaps | 結論、測試範圍與適用邊界、四態統計、缺陷摘要、三個統計指標、未測理由;工時與放行決策須人工。複驗鏈指向案例趨勢(跨版本,不在單次報告內) |
| T08 送審檢驗表 | 結案與交付 | — | 輸入是各平台送審檢查項,且不代替平台正式審查結果 |
| T09 效能測試需求與腳本 | 健檢與專項 | — | 是量測前的需求與腳本,屬測試輸入 |
| T10 適配性測試需求 | 健檢與專項 | — | 是裝置母體條件與方案;單次執行只覆蓋一個裝置組合 |
| T11 自動化測試需求 | 健檢與專項 | — | 是腳本製作需求與可執行性確認,屬測試輸入 |
| T12 自動化結果與數據分析 | 健檢與專項 | **derived** | 逐筆結果(逐局帳,見下)、分析資料、執行摘要、排除的讀錯值 |
| T13 效能與自動化專項結案 | 健檢與專項 | gaps / — | 有量測到效能指標才產生;核定門檻須由知識庫提供 |
| T14 使用體驗與白紙研究紀錄 | 研究與支援 | — | 人工使用體驗研究紀錄 |
| T15 競品數據與研究分析 | 研究與支援 | — | 競品資料不在受測版本的證據範圍 |
| T16~T18 訓練需求與考核 | 教育與支援 | — | 人員訓練規劃與考核 |
| T19 測試排程與交付追蹤 | 研究與支援 | — | 排程管理 |

T13 的產生條件只看「有量測到的效能指標」。穩定性指標(例如閃退次數)就算沒有裝置取樣也一定算得出來,拿它當依據會讓每次執行都長出一份沒有量測值的專項結案。

空表格一律附 `emptyReason`。沒有缺陷的執行,問題清單會寫「本次執行未開立遊戲缺陷」,因為一張沒有說明的空表會被讀成「已驗過且沒問題」。

### T12 逐筆結果是一份逐局帳

原表的欄位是 `資產前 | 操作數值 | 累積操作值 | 結果值 | 特殊結果A~C` —— 一局一列的下注與派彩帳,不是步驟清單。由 `spinTransactions()` 重建:它已經排除 AutoSpin 累計、Bonus 一次結算、以及 runner 回報「沒等到畫面靜止」的讀值,那些回合的數字不能當成單局結果。

- 資產前 = 結算後餘額 − 本局派彩 + 本局下注(讀到餘額才算)。
- 累積操作值逐局累加。
- 餘額遞推鏈斷掉的那一列會標註「累積值不連續」(中間有未納入的餘額變動,例如非拉霸入帳)。
- 非拉霸玩法重建不出逐局帳時,寫明原因並指向報告的逐步證據章節,不改用步驟傾印充數。

### T03 的兩個平台欄位不會被壓成一欄

原表一列同時記 `平台A結果` 與 `平台B結果`。一次執行只涵蓋一個平台,所以平台A填本次結果,平台B全列「未測」並列入 `unfilled`。讓那一欄消失會讓讀者以為本表已涵蓋兩個平台 —— 原始紀錄就警告過,一個平台的 PASS 不能推定另一個平台已測。

## 6. 資料量

整份文件集跟著報告回應一起送出,而逐筆證據可達數百列。逐列表格有列數上限(預設 400,`QaDocOptions.maxRows` 可調),超過只截斷列,並在 `emptyReason` 寫明被截掉多少列與完整資料在哪一章節 —— 不靜默刪資料。

## 6.1 匯出

報告的「交付文件」一節有匯出鈕,產生單一 `.xlsx`:

| 工作表 | 內容 |
|---|---|
| 總覽 | 規範版本、內部標準版本、產生時間、覆蓋狀態統計、說明 |
| 原有統計指標 | 三個指標的分子、分母、值、納入範圍與定義界線 |
| 文件覆蓋 | 19 類文件逐列:代碼、名稱、群組、覆蓋狀態、原因、需人工補填欄位 |
| 各文件一張 | 可產生的文件,各含表頭、工作紀錄、關聯紀錄與補填提示 |
| 分級對照 | 四態、A~D 級、E0~E3 的來源定義 |

不可產生的文件**不另開工作表**(那只會是一張空表),但仍在「文件覆蓋」逐類列出原因。空表與被截斷的表,其 `emptyReason` 會一併寫進檔案 —— 收到檔案的人不該把空白讀成「已驗過且沒問題」。算不出來的統計指標寫「不計算」而非 `0%`,因為 `0%` 會被讀成「一項都沒通過」。

實作分兩層:`web/.../qaDocsExport.ts` 是純函式,負責資料整形與工作表名稱清洗(Excel 的 31 字上限與 `[]:*?/\` 禁用字元是硬限制,違反會讓整個檔案打不開,所以截斷與去重都在這裡做完並有測試);`QaDocsPanel` 只負責寫檔,並沿用測試項目匯入頁的慣例以動態 `import('xlsx')` 延遲載入 —— SheetJS 約 500 kB,獨立成 chunk 才不會拖慢其他頁面。

## 6.2 平台可執行範圍宣告

AI 測試平台最危險的失效模式不是測失敗,是**報告看起來很完整**。一份全綠的報告,如果它涵蓋的是測試實務裡的一部分,而剩下的連「做不到」都沒寫,那份報告會被當成放行依據 —— 這比測出一堆缺陷糟得多。

所以能力宣告是**資料**(`infra/lambda/api/report/qaCapability.ts`),不是文件裡的一段散文:跟著每份報告輸出、有測試鎖住,改了平台能力就要改宣告,不改就會跟報告對不上。

分級只有三種,刻意不留中間地帶:

| 分級 | 意思 |
|---|---|
| `automated` | 平台可自動產生這一類的判定證據 |
| `partial` | 可產生部分證據,但有明確缺口(`covers` / `gap` 兩欄分開寫) |
| `not_supported` | 結構性做不到;任何一次執行都不會有證據,需人工或別的工具 |

每一條 `partial` 與 `not_supported` 都必須同時寫出 `gap`(做不到什麼、為什麼)與 `fallback`(缺口怎麼補),由測試強制。

### 幾條關鍵的誠實標示

- **M08 影音語系**:`not_supported`。可以讀出當下語系、可以看出破圖缺字,但**音訊軌未擷取**(音效時機與破音無從判定),而且**沒有核定文案可對照**(各語系的文字與版面是否正確,判定基準本身不在平台內)。
- **M09 網路通訊**:`partial`,而且缺口要分兩件事講 —— **觀察得到**遊戲自己斷線,但**施加不了**指定的延遲或丟包。任何寫明「延遲 N ms」或「掉包 N%」的測項永遠不在可執行範圍內。只寫「未觀測到斷線」會讓人以為重測可能就有。
- **M15 設備周邊**:`not_supported`。出票、投幣、搖桿、實體燈號屬機台硬體,平台沒有實體 I/O。
- **M04 資產帳務**與 **M12 效能**:`automated`,而且是強項 —— 帳務由畫面讀值**重建成帳**再對帳,不採用 AI 自報。

### 不把客戶的測項數量寫進程式

各分類的實際占比必須從專案自己的測項庫即時統計。把某一次快照的數字寫死在程式裡,既是把客戶資料帶進開發,也會過期。

摘要句因此明寫「分類數不等於測項數」:**19 類裡有幾類可執行,不能當成涵蓋率**。做不到的那幾類如果剛好是客戶測試量最大的幾類,「19 類中 8 類可自動執行」會嚴重高估實際涵蓋。

## 6.3 弱網條件:只有真的套用了才能主張

弱網測項寫的是具體條件(「延遲 1000ms」「掉封包 10%」)。報告要主張「這個條件下驗過」,前提是**真的施加了那個條件**。最糟的結果是案例寫了 1000ms、實際沒生效、報告照樣寫弱網通過 —— 那比測不到還糟。

所以施加紀錄(`agent/networkConditions.mjs`,寫進 `report.networkConditions`)刻意分成三塊:

| 欄位 | 意思 |
|---|---|
| `requested` | 案例要求什麼 |
| `applied` | 實際套上的是什麼 |
| `unsupported` | 要求了但這個後端做不到的項目(附原因) |

`verified` 預設 **false**,而且「有量測」也不足以翻成 true:要求 1000ms 卻量到 3ms,代表工具收下了參數但條件沒套到實際路徑上。`confirmsLatency()` 會比對量值與要求值,落差過大就維持 false,報告寫「已施加、未經獨立量測確認」。

### 條件從哪裡來

案例 YAML 寫一行 `network:`,例如:

```yaml
name: 弱網下完成購買
network: latency=1000,loss=5
task: 進入商城並完成一次購買
```

路徑刻意收斂成一處解析:提交時由 `extractCaseNetwork()` 取出並快照進 `job.json`,之後 `emulator` 的 `run.sh` 與 `web` 的 engine 都讀同一份。兩個後端各自解析案例 YAML 的話,同一個案例可能在不同後端得到不同條件,而報告會以為自己驗的是案例寫的那一個。

三層職責不重疊:`extractCaseNetwork()` 取出來、engine 的 `sanitizeNetworkSpec()` 把關形狀(長度與字元,因為這個值會進容器環境變數)、runner 的 `parseNetworkCondition()` 解析語意。解析刻意保守:看不懂的鍵**忽略而不是猜**。

### 報告的四種陳述

適用邊界的網路條件欄依實際情形分四種,主張強度完全不同:

| 情形 | 報告怎麼寫 |
|---|---|
| 施加成功且量測確認 | 「已施加 延遲 1000ms(延遲經獨立量測確認:實測 1010ms,施加前 2ms);結論僅適用於這個網路條件」 |
| 施加成功但未確認 | 「已施加 …(僅工具回報施加成功,未經獨立量測確認)」 |
| 施加成功但有做不到的項目 | 「已施加 …;但要求的 lossPct 這個後端做不到,該項不得視為已驗」 |
| 施加失敗 | 「施加失敗(原因);本次是一次沒有網路條件的普通執行;不得主張弱網已驗」 |
| 沒要求 | 「未施加任何網路條件…不得主張弱網與中斷復原行為已驗」 |

### 各後端的能力差異

| 後端 | 延遲 / 頻寬 | 丟包 | 離線 |
|---|---|---|---|
| `emulator`(Android 容器) | ✅ `tc netem` | ✅ | ⚠️ 全丟封包,介面仍 up |
| `web`(瀏覽器) | ✅ 開發者協定 | ❌ 協定沒有這個旋鈕 | ✅ |
| `devicefarm`(雲端真機) | ❌ 遠端存取工作階段不接受網路設定檔 | ❌ | ❌ |
| `windows`(主機) | ❌ 需封包過濾驅動 | ❌ | ❌ |

做不到的後端在被要求時會寫一筆 `ok: false` 的紀錄,不是靜默忽略 —— 案例要求過這件事必須留在報告裡。

### 容器塑形的兩個關鍵限制

**塑形只套進容器的網路命名空間。** `explorationRunner` 跑在同一台 EC2 主機上,要連推論服務、要把截圖與報告傳上物件儲存。在主機的對外介面套 netem 會把 runner 自己的流量一起劣化,然後報告會把推論逾時與證據上傳失敗算成「遊戲在弱網下壞掉」。那是假的失敗。

**adb 控制通道必須排除在塑形之外。** 這不是最佳化,是功能能不能用的前提。adb 走 host → 容器的 5555 埠,容器的回應封包與遊戲流量走同一個 qdisc。不排除的話,`offline` 會直接切斷 adb(任務整個失敗,表面上像遊戲崩潰),限速會讓每張數百 KB 的截圖花十幾秒(探索迴圈慢到逾時)。所以 qdisc 用 `prio` 分兩條路:5555 的封包走不受限的 band,其餘走 netem。`priomap` 全填 `2` 是必要的 —— `prio` 預設依 TOS 把多數封包放進 band 0,沿用預設會讓遊戲流量**不**受塑形,跟需求正好相反。

另外「離線」在容器裡是全丟封包而不是鏈路斷開:介面仍為 up,系統不會回報「無網路」,程式收到的是逾時。測斷網提示的測項因此測不到它要測的東西,這一點記在 `unsupported` 的 `offline.linkDown`,並寫進 M09 的能力缺口。

測試:`infra/test/network-conditions.test.ts`、`infra/test/netem-shaper.test.ts`、`infra/test/network-spec-plumbing.test.ts`。

## 6.4 音訊:量不到聲音不等於沒有聲音

音訊範疇先前被標成「結構性做不到」,理由寫「runner 未擷取音訊軌」。那是**低報** —— 平台一直在收音訊:

| 來源 | 收什麼 |
|---|---|
| `recording`(裝置後端) | 整場錄影含聲音,ffmpeg 算每 0.1 秒的 RMS(dB) |
| `host_meter`(Windows) | 每步一次的輸出音量峰值(WASAPI),另有自我檢查驗證擷取鏈 |

證據收了卻宣告做不到,跟高估一樣是準確性問題,只是方向相反。問題出在這些量測只寫進 `audio/levels.json` 與 `devlogs/`,沒有進 `report.json`,所以判定端看不到。

`agent/audioEvidence.mjs` 把它們彙整成 `report.audioEvidence`,而結論刻意分三態:

| `verdict` | 意思 | 可以主張什麼 |
|---|---|---|
| `audible` | 量到聲音 | 有音訊輸出,且知道出現在哪些時刻 |
| `silent` | 擷取鏈已驗證但整段無聲 | 本次無聲音(是缺陷線索) |
| `unknown` | 擷取鏈未驗證且整段無聲 | **什麼都不能主張** |

三態的理由只有一條:**量到聲音是強證據,量不到不是。** 整段沒量到可能是遊戲真的沒出聲(缺陷),也可能是擷取沒抓到(工具問題)。錄影路徑沒有自我檢查可以分辨,所以那種情況一律 `unknown`。把它寫成「無音效」會憑空生出一個缺陷報告 —— 這條紀律 Windows 那條路早就有了(`audioSelfTest` 不通就直接停用聲音判斷),現在錄影路徑也遵守同一條。

而且就算 `audible`,也只能主張「有聲音、在這些時刻」。**音效是否正確需要參考音軌可對照,平台沒有** —— 跟語系文案是同一種缺口:讀得到語系 ≠ 文案正確,量得到聲音 ≠ 音效正確。

### 範疇的可偵測性改成動態

音訊**不在** `SCOPE_GAP` 裡。那份表的語意是「重測也不會有」,而音訊在裝置後端量得到,寫成靜態缺口等於把一個可修的設定問題宣告成永久限制。所以:

| 情形 | status | `detectable` | 理由 |
|---|---|---|---|
| 量到聲音 / 已驗的無聲 | `executed` | `true` | — |
| 有量測但無定論 | `not_executed` | `true` | 本次無法下結論(附原因) |
| 完全沒有量測 | `not_executed` | `true` | 本次沒有音訊量測,並點明網頁與容器後端沒有擷取 |
| 樣板沒選此範疇 | `not_applicable` | `true` | 未選定(**不是**「沒量到」) |

最後一列是刻意的:範疇沒被選定時說「本次沒有音訊量測」會把讀者引去查一個不存在的問題。

M08 因此從 `not_supported` 改為 `partial`。缺口仍然寫清楚:沒有參考音軌、沒有核定文案、網頁與容器後端沒有擷取。

測試:`infra/test/audio-evidence.test.ts`。

## 7. 確定性

`buildQaDocumentSet()` 是純函式,`generatedAt` 預設取報告的測試結束時間而非當下時間,因此同一份證據永遠投影出同一份文件集,與報告引擎的確定性保證一致。

## 8. 版本

`QA_DOC_STANDARD_TAG`(目前 `QA-DS-1.0`)寫在每個文件集上,並同時記錄產生它的內部標準版本(`internalStandard`),兩套語彙的對應關係可回溯。對應規則改版時要調升版本號。
