# 驗收標準與測試報告規範(PA-AS 1.0)

一次測試只有一個結論。任務列表、任務詳情、報告封面、通過率統計都讀同一個值:報告引擎依本標準算出的 **測試結論(verdict)**,存在 `jobs/<jobId>/verdict.json`。

實作:`infra/lambda/api/report/acceptance.ts`(驗收項目與結論)、`infra/lambda/api/report/rtpLedger.ts`(RTP 帳務)、`infra/lambda/api/report/engine.ts`(AI 回報的佐證規則)。測試:`infra/test/report-acceptance.test.ts`。

## 1. 兩個名詞,不再混用

| 名詞 | 來源 | 值 | 意思 |
|---|---|---|---|
| 執行結果(state) | runner `status.json` | 執行完成 / 未完成 / 錯誤 / 已取消 / 超出預算 / 逾時中斷 | AI 有沒有走完流程。「執行完成」只代表 AI 宣告完成,**不代表通過** |
| 測試結論(verdict) | 報告引擎(本標準) | 通過 / 通過(有風險)/ 失敗 / 受阻 | 案例要求有沒有被證據證明達成 |

2026-10-12 之前,列表顯示的是執行結果(AI 說 done 就是綠勾),報告封面顯示的是另一套規則算的結論,兩者會互相矛盾(job-mv3xfeax:列表通過、報告失敗)。

## 2. 結論判定規則

用語對齊 ISTQB:實際結果符合預期 = 通過;不符合 = 失敗;無法執行或無法得出結果 = 受阻。

1. **失敗(FAIL)**:任一「必要」項目不通過,且歸因為 **遊戲本身**(確定性證據,或已確認的遊戲缺陷)。
2. **受阻(BLOCKED)**:任一「必要」項目不通過或無法判定,但原因不是遊戲:執行未依協定、環境、AI 代理、數據不可溯源。這次結果 **不能作為驗收依據**,需修正後重測。
3. **通過(有風險)(PASS_WITH_RISK)**:必要項目全部通過,但有「建議」項目不通過、待判讀異常,或 Critical / High 風險。
4. **通過(PASS)**:全部項目通過。

優先序:失敗 > 受阻 > 通過(有風險)> 通過。已確認的遊戲缺陷即使測試沒跑完也要呈現為失敗。

通過率 = 通過(含有風險)÷(通過 + 失敗)。受阻不進分母,因為那次測試沒有得出結果。

## 3. 驗收項目

每個項目都記錄:等級(必要 / 建議)、要求、要求來源(案例原文或參考標準)、門檻、實際值、結果、歸因、判定依據(程式判定 / AI 判讀)、證據步驟。報告上的證據步驟可直接點開當步截圖。

### 通用(所有測試)

| ID | 等級 | 項目 | 門檻 | 不通過的歸因 |
|---|---|---|---|---|
| AC-G01 | 必要 | 測試流程執行完成 | 依案例走到完成條件,不是被時間 / 步數 / 預算上限、取消或錯誤中止 | 測試執行 / 環境 / AI 代理 |
| AC-G02 | 必要 | 執行期間無閃退 | 閃退 0 次(runner 每步查 App 程序狀態) | 遊戲 |
| AC-G03 | 必要 | 無已確認的 Critical / High 遊戲缺陷 | 0 個 | 遊戲 |
| AC-G04 | 建議 | 沒有待人工判讀的異常 | 0 項 | 測試執行 |
| AC-G05 | 建議 | AI 測試代理行為可靠 | Medium 以上的 AI 問題 0 項 | AI 代理 |

### 拉霸 RTP 量測(案例提到 RTP / 派彩率 / 回報率時套用)

| ID | 等級 | 項目 | 門檻 |
|---|---|---|---|
| AC-S01 | 必要 | 付費旋轉樣本數達標 | ≥ 案例要求局數(從案例原文讀,例如「玩滿 500 局」);局數由 AutoSpin 計數遞減加總,不採用 AI 自報 |
| AC-S02 | 必要(案例要求固定投注時)| 投注額全程固定 | 投注額變更 0 次 |
| AC-S03 | 必要(案例要求實讀時)| 統計數字皆為畫面實讀 | AI 結論中的估計值 0 筆(約、估算、推斷、待核對、遮擋…) |
| AC-S04 | 必要 | 非拉霸收入已逐筆分離 | 量測區間內的贈送,金額未確認 0 筆 |
| AC-S05 | 必要 | RTP 可由證據重算 | 淨 RTP 可由帳務公式算出 |
| AC-S06 | 建議 | RTP 與理論值無顯著差異 | \|z\| ≤ 2.576(99% 雙尾);需要知識庫提供 `expectedRtp` |

## 4. AI 回報的佐證規則

AI 看圖的回報是 **證據線索**,不是結論。

- 「按了沒反應」類的缺陷,回報前 8 步內必須有實際的點擊 / 長按等操作紀錄。完全沒有操作紀錄 → 改列為 AI 測試問題(「AI 回報的缺陷沒有對應的操作紀錄」),不算遊戲缺陷。有操作但畫面都有變化 → 列為待判讀。
- 「按了沒反應 / 卡死」代表只有重啟才救得回來。如果回報之後、在任何重啟之前,同一畫面的操作又生效了(畫面有變),回報就被後續證據推翻 → 列為待判讀。常見原因是 AI 座標偏移、截圖尺寸改變、動畫還沒結束。
- AI 觀察型缺陷要 **可重現** 才算已確認:至少 2 個步驟都看到,且平均信心 ≥ 0.5。只看到一次,即使信心很高,也列為待判讀。待判讀會讓結論變成「通過(有風險)」,不會單憑一張截圖就判遊戲失敗。
- 斷線、重連、帳號在另一裝置登入、逾時等連線類回報,一律列為待判讀。雲端真機的網路與帳號狀態屬於測試環境,需要對照伺服器紀錄,或在穩定網路下重現,才能歸因給遊戲。

## 5. RTP 帳務(可溯源)

**方法**:餘額差法(AutoSpin)。AI 只讀畫面上的數字(AutoSpin 剩餘局數、餘額、投注額),由程式計算。

- **量測區間**:同一連線段、同一投注額、AutoSpin 計數連續遞減的一段。重開 AutoSpin(計數回升)、換投注額、換連線都會切開。區間之間的餘額變化一律不計(例如在大廳領的登入獎勵)。
- **區間內**:付費局數 = 計數遞減;投注 = 局數 × 投注額;餘額變化 = 末筆 − 首筆。
- **非拉霸收入**(升級 / 任務 / 登入 / 活動贈送),金額依據依優先序:
  1. `obs.non_slot_credit`:AI 在彈窗上清楚讀到的數字。
  2. 餘額差:事件前後的餘額,而且中間沒有旋轉,屬於確定性結果。
  3. AI 說明中寫出的入帳金額。
  4. AI 明確寫「沒有贈送」→ 記 0。
  5. 沒有任何入帳描述 → 記 0,並標示供人工確認。
  6. 估計 / 遮擋 / 待核對 → **無法確認**。量測區間內有任何一筆無法確認,淨 RTP 就不可算。
- **公式**:淨 RTP =(Σ區間餘額變化 − Σ區間內非拉霸收入 + Σ投注)÷ Σ投注。報告同時列出未扣贈送的上限值。
- **統計精度**:σ = 單局報酬標準差(投注額倍數),取自 PAR 表(知識庫 `rtpStdDev`);沒提供時用 6,並標示為假設值。95% 信賴區間半寬 = 1.96σ ÷ √n;誤差 ±1 個百分點所需局數 =(1.96σ ÷ 0.01)²。σ = 6 時,500 局的信賴區間約 ±52 個百分點,約需 138 萬局才能到 ±1 個百分點。

**結論的意義**:實機抽樣 500 局只能做合理性檢查(帳務是否一致、有沒有離譜的偏差),不能證明 RTP 合規。博弈機的理論 RTP 由數學模型(PAR 表)與 RNG 認證證明:GLI-11 預設下限 75%,各司法管轄可調高,例如 Massachusetts 205 CMR 143.01 改為 80%。社交博弈(不能兌現)不在真錢博弈規範內,沒有法定 RTP 下限,但 RTP 仍應與遊戲內公告一致。

## 6. 報告內容(對齊 ISO/IEC/IEEE 29119-3 測試完成報告)

| 章節 | 內容 |
|---|---|
| 封面 | 結論、發布建議(不能比結論樂觀:結論失敗 → 不可發布;結論受阻 → 受阻)、案例版本、裝置、模型 |
| 驗收結論與標準 | 結論與理由、決定結論的項目、逐項驗收表(每項附證據步驟)、RTP 帳務(量測區間、非拉霸收入、公式、統計精度)、判定規則、參考標準 |
| 測試範疇 | 每個範疇的狀態,未執行者附理由並標明平台能否偵測(見 6.2) |
| 適用邊界 | 統計截止點、實際受測組合、未變動的維度、不得延伸的主張(見 6.2) |
| 其餘章節 | 執行摘要、判定明細、缺陷(遊戲缺陷與 AI 測試問題分開)、數據品質(排除的讀錯值與投注變更)、逐步證據(截圖 + AI 觀察 / 理由 / 讀值) |

## 6.2 主張紀律:報告只能主張證據支持的範圍

一份報告最常見的誤用,是把「一次執行、一個組合」的結果讀成普遍成立。以下三件事因此必須外顯,而不是留給讀者推斷。

### 「未測」有兩種意思,要分開

| `detectable` | 意思 |
|---|---|
| `true` | 平台收得到這類證據,本次沒走到;重測有機會補上 |
| `false` | 平台目前沒有這類偵測器,**任何一次執行都不會**有證據 |

`animation`、`audio`、`multiplayer`、`localization`、`save_load`、`payment`、`ai_behavior`、`physics` 屬後者,各自在 `SCOPE_GAP`(`engine.ts`)寫明缺口原因。把工具缺口也印成「未測」,讀者會以為「這次剛好沒測到」,從而高估這份報告的覆蓋範圍。每個非 `executed` 的範疇都帶 `reason`。

### 門檻要標來源

`release.thresholdSources` 逐項標出 `knowledge_base`(客戶核定)或 `platform_default`(平台預設的顧問參考值)。合併成一個數字後來源就看不出來了,但這個區別決定了它能不能當允收依據:平台預設不是客戶核定值,也不能跨專案套用 —— 歷史門檻的裝置分級、量測工具與取樣條件各不相同。

### 適用邊界要明文

`claimScope` 載明:

- **統計截止點**:所有數字都是到這一刻為止的證據算出來的。
- **實際受測組合**:平台、OS、裝置、解析度、版本、環境、區域、語系。讀不到的維度標 `observed: false`,不留白 —— 留白會被當成「那個維度已驗」。
- **未變動的維度**:單一版本 → 不能證明修正複驗或版本回歸;單一裝置 → 不得主張跨機型適配;未施加網路劣化 → 不得主張弱網與中斷復原;單一連線段 → 不涵蓋長時掛測的跨段行為。

### 語系:觀察得到,但不等於驗過

`GLOBAL_PROFILE` 有 `locale` 觀測欄位,AI 每步在畫面文字明確看得出來時回報當下語系(看不出來就省略,不准猜)。適用邊界因此能寫出本次實際跑在哪個語系,而不是一律「未觀測」。

三種情況的主張強度不同,報告分開寫:

| 觀測到的語系數 | 可以說的 |
|---|---|
| 0 | 未觀測到語系,不得主張任何語系的顯示已驗 |
| 1 | 本次只跑在該語系,不得主張其他語系 |
| ≥2 | 語系切換確實發生過 |

**但三者都不足以主張「文案正確」。** 判定文案與版面要對照核定文案,平台沒有核定文案可對照 —— 所以 `localization` 範疇仍標為平台限制,缺的是比對基準,不是語系偵測。`claimScope.statements` 會明寫:語系是 AI 的畫面判讀,只說明跑在哪個語系,不構成語系正確性的驗證。
- **聲明**:通過表示該項預期與實際相符,不表示同一畫面沒有其他未被檢查的問題。

## 6.3 趨勢與 flaky 也讀同一個結論

第 1 節的區分不只適用於報告封面。案例趨勢(`infra/lambda/api/trends.ts`)原本以 `status.state` 計算通過率與 flaky —— 那是執行結果,不是測試結論,等於在另一個地方重犯「列表通過、報告失敗」的錯。現在趨勢分析:

- 優先讀 `verdict.json` 的結論;`PASS` 與 `PASS_WITH_RISK` 算通過,`FAIL` 算失敗,`BLOCKED` 不進通過率分母(與第 2 節一致)。
- 沒有結論的舊任務才退回執行結果,並在 `verdictCoverage` 標明有多少筆是退回的 —— 依據混雜時,通過率的意義會被稀釋,要讓讀者看得到比例。
- flaky 偵測在同一產物版本內**不混用依據**:只要該版本有依結論判定的點,就忽略退回執行結果的點。否則「執行完成但結論失敗」那一次會被算成通過,憑空造出一個 flaky。

### 修正複驗鏈

`CaseTrend.retest` 由跨任務歷史建立(同一 `appId` + `caseId`,依產物版本分段):

- `links`:某版本失敗、之後的**新版本**通過 → 一筆複驗。同一版本重跑通過不算複驗(被測沒有變更)。
- `unresolved`:失敗後沒有任何後續版本通過。
- **原版本的失敗不被覆寫**。複驗通過只代表後續版本通過;用新版本的結果蓋掉舊版本的失敗,會讓這份歷史看起來從沒出過問題。段內出現過失敗,該段就記失敗。

複驗鏈刻意**不放進報告引擎**:引擎是純函式、只看單次執行的證據(第 5 節的確定性保證)。跨版本彙整需要讀其他任務,屬 API 層。

### 趨勢徽章也要照這條線

`CaseTrendBadge` 的結果點原本畫 `state`,所以結論失敗的那一次會顯示成 ✓ —— 在最顯眼的地方重犯同一個錯。現在:

- 結果點畫 `recent[].outcome`(結論);受阻有獨立符號 `⊘`,不混進通過或失敗。
- 退回執行結果算出的點用虛線框,通過率加 `*` 並附說明 —— 依據較弱必須看得出來,否則兩種強度完全不同的通過率長得一模一樣。
- 複驗狀態直接顯示「已複驗 N / 未複驗 M」。
- 舊版後端沒有 `outcome` 時退回原本的符號表,不會空白。

測試:`infra/test/trends-verdict.test.ts`、`web/src/components/CaseTrendBadge.test.tsx`。

## 6.5 效能指標:單位要能對上門檻

外部效能門檻常以「卡頓率 < 1%」「耗電量 < 10%」這類形式出現,而平台原本算的是 `frame_time_p95`(毫秒)與 `battery_drain`(mAh)—— **單位不同,無法比對**。拿 mAh 去對 10% 不是判寬鬆或嚴格,是比了兩個不同的量。因此補上三個指標:

| 指標 | 計算 | 說明 |
|---|---|---|
| `stutter_rate` | 幀時間 ≥ `stutterFrameMs` 的幀數 ÷ 總幀數 | 預設界線 32ms(約低於 31 FPS)。界線可由知識庫覆寫 —— 「卡頓」各家定義不同,比對前要先對齊 |
| `frame_time_stddev` | 幀時間直方圖的標準差(ms) | 離散程度,越小越穩 |
| `battery_drain_pct` | `battery_drain` ÷ `batteryCapacityMah` | 容量未知就回 null,不以 mAh 充當百分比 |

**`frame_time_stddev` 不是任何外部「穩幀指數」的換算值。** 只給門檻值而沒有公式的指數無法對應;要用它判定允收,得先取得對方的定義並確認一致。這一點寫在指標的 `description` 裡,報告上看得到。

測試:`infra/test/report-perf-metrics.test.ts`。

## 6.4 部署閘門含型別檢查

`vitest` 只轉譯、不做型別檢查,所以單靠測試會讓型別錯誤一路部署出去(實際發生過:一個測試檔的 `category` 被推斷成 `string` 而非 `FindingCategory`,測試全綠,只有 `tsc` 抓得到)。閘門現在先跑三個 workspace 的 `typecheck`,再跑測試;順序由 `infra/test/updater-stack.test.ts` 鎖住。

## 6.1 交付文件投影

客戶品檢流程用的是另一套語彙(PASS / FAIL / BLOCK / N-A、A~D 級缺陷、E0~E3 發現分級)與另一套統計公式。報告會額外附一節「交付文件」,把本標準的判定重新表述成那 19 類交付文件 —— 只換語彙與版面,**不重算結論**。規則見 [交付文件規範(QA-DS 1.0)](./qa-report-standard.md)。

兩套通過率的分母不同(本標準:通過÷(通過＋失敗);交付文件:PASS÷執行總數),報告一律並列並標明分母,不互相取代。
